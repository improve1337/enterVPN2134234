# Ключи доступа — управление из админки бота

Документ описывает подсистему ключей в основном боте (`bot/`): как админ создаёт
ключи, выдаёт их по Telegram ID или `@username`, как ключ появляется при оплате и
как отзывается доступ. Актуально на 7 ноября 2026.

---

## 1. Что такое ключ

**Ключ** — единица выдачи доступа. Это человекочитаемый код вида
`ENT-AB12-CD34`, который привязывается к получателю и превращается в подписку
Marzban со ссылкой-подпиской.

Ключ нужен, чтобы:

- выдать доступ вручную (продажа в обход бота, подарок, тест);
- видеть, кто и когда получил доступ, и отзывать его;
- не плодить пользователей Marzban: подписка одна на Telegram ID, ключи её
  продлевают.

Ключи создаются двумя путями:

1. **Админом** — вручную через «🛠 Админка» → «🔑 Ключи» или командой `/key`.
2. **Автоматически** — при активации подписки (пробный доступ или оплата).

---

## 2. Модель данных

Таблица `keys` (SQLite, `src/db.ts`):

| Поле | Смысл |
|---|---|
| `code` | PK, код ключа `ENT-XXXX-XXXX` |
| `plan_code`, `plan_name` | тариф на момент выдачи (снапшот) |
| `days`, `traffic_limit_gb` | срок и лимит из тарифа (снапшот) |
| `status` | `new` / `issued` / `active` / `revoked` / `expired` |
| `note` | заметка админа |
| `created_by` | кто создал (`NULL` — автоматически) |
| `created_at` | когда создан |
| `target_telegram_id` | получатель, если известен |
| `target_username` | `@username` без собаки, в нижнем регистре |
| `marzban_username` | имя пользователя в Marzban (`tg_<id>`) |
| `subscription_url` | ссылка-подписка |
| `issued_at`, `activated_at`, `expires_at` | сроки |
| `revoked_at`, `revoked_by` | кто и когда отозвал |
| `order_id` | заказ, если ключ появился из оплаты |

Индексы: `status`, `target_telegram_id`, `target_username`, `marzban_username`.

## 3. Статусы и переходы

```
            createKeys (админ)
                  │
                  ▼
                ┌─────┐   выдать по @username, юзер неизвестен
                │ new │ ────────────────────────────────────► ┌────────┐
                └─────┘                                       │ issued │
                  │                                           └────────┘
                  │ выдать по ID / известному @username          │ юзер написал боту
                  ▼                                              ▼
                ┌────────┐   срок истёк   ┌─────────┐
                │ active │ ─────────────► │ expired │
                └────────┘                └─────────┘
                  │
                  │ revokeKey
                  ▼
                ┌─────────┐
                │ revoked │
                └─────────┘
```

- `new` — код создан, никому не выдан.
- `issued` — выдан по `@username`, получатель ещё не запускал бота. Ключ
  активируется автоматически при первом его сообщении.
- `active` — привязан к Telegram ID, подписка выдана.
- `revoked` — отозван админом.
- `expired` — срок истёк. Статус выставляется лениво: при чтении карточки и при
  построении списка (`markExpiredKeys`).

## 4. Сценарии

### 4.1. Создать ключ

«🛠 Админка» → «🔑 Ключи» → «➕ Создать ключ» → выбрать тариф.
Или командой:

```
/key new vpn_1m подарок
```

Срок и лимит берутся из тарифа и сохраняются в ключе. Ключ получает статус `new`.

### 4.2. Выдать ключ

По Telegram ID (доступ активируется сразу, пользователю уходит сообщение):

```
/key issue ENT-AB12-CD34 8460184787
```

По `@username`:

```
/key issue ENT-AB12-CD34 @vasya
```

- Если пользователь уже писал боту — ключ активируется сразу.
- Если нет — ключ переходит в `issued` и активируется сам, когда `@vasya`
  впервые напишет боту (привязка происходит на каждом апдейте).

То же кнопками: «🔑 Ключи» → «📤 Выдать ключ» (сначала код, потом получатель).

### 4.3. Оплата

После подтверждения оплаты `fulfillPaidOrder` вызывает `activatePlan`, который
выдаёт подписку и **заводит или продлевает личный ключ пользователя**:

- первый платёж/пробный — создаётся ключ со статусом `active`, в `order_id`
  пишется заказ;
- повторная покупка — тот же ключ продлевается (срок считается от текущего),
  `order_id` обновляется на последний заказ.

Пользователь получает ту же ссылку-подписку, что и раньше: тариф меняет срок и
лимит, а не URL.

### 4.4. Отозвать ключ

```
/key revoke ENT-AB12-CD34
```

или кнопкой в карточке ключа (с подтверждением).

Поведение:

- ключ получает статус `revoked`;
- доступ в Marzban выключается (`status: disabled`) **только если** у
  пользователя не осталось других действующих ключей;
- если доступ выключен, срок подписки в боте обнуляется — «📦 Моя подписка»
  покажет «Истекла»;
- получателю уходит уведомление.

Повторная выдача того же кода после отзыва запрещена — создайте новый ключ.

## 5. Команды и кнопки

| Действие | Команда | Кнопка |
|---|---|---|
| Справка | `/key` | — |
| Создать ключ | `/key new <тариф> [заметка]` | ➕ Создать ключ |
| Список | `/key list` | 📋 Список ключей |
| Карточка | `/key info <код>` | 🔎 Найти ключ |
| Выдать | `/key issue <код> <id\|@username>` | 📤 Выдать ключ |
| Отозвать | `/key revoke <код>` | 🚫 Отозвать (в карточке) |
| Ссылка | `/key link <код>` | — |

Тарифы: `vpn_1m` (30 дней), `vpn_3m` (90 дней). Оба безлимитные, до 5 устройств.

Все действия доступны только админам (`ADMIN_IDS` + назначенные через панель).
Каждое действие пишется в `audit_log`: `key_created`, `key_issued`, `key_bound`,
`key_revoked`.

## 6. Нюансы и принятые решения

| Ситуация | Решение |
|---|---|
| Имя пользователя в Marzban | `@username` из Telegram (например `geqemi`), иначе `tg_<telegram_id>`; в поле `note` — `tg:<id>` для защиты от коллизий |
| Одна подписка на пользователя | ключи продлевают того же Marzban-пользователя, а не создают новых |
| Ссылка при смене тарифа | URL не меняется — меняются срок и лимит; так клиенту не нужно переимпортировать подписку |
| Повторная покупка | Тот же личный ключ продлевается от текущей даты; новые записи не плодятся |
| Ключ выдан по `@username` | Хранится в `issued`; привязка при первом апдейте от этого пользователя |
| Username изменён | Привязка по старому нику не сработает — выдайте ключ по Telegram ID |
| Отзыв одного из нескольких ключей | Доступ выключается только если других активных ключей нет |
| Истечение срока | Статус `expired` ставится лениво при чтении/списке; доступ в Marzban при этом не выключается автоматически (см. §7) |
| Идемпотентность выдачи | `provisionSubscription` делает `PUT` для существующего пользователя, повторная выдача не создаёт дублей и не сбрасывает трафик |
| Коды | Алфавит без `0/O`, `1/I/L`; 8 случайных символов (`crypto.randomInt`), уникальность проверяется по БД |
| Лимит пачки | До 50 ключей за вызов `createKeys` |
| Mock-режим | `MOCK_MODE=true` — выдача эмулируется, ссылка вида `<MOCK_LANDING_URL>/sub/tg_<id>/<token>`; всё остальное поведение то же |
| Безопасность | Ключи не отдаются через HTTP-API бота — только в чате админа; коды не логируются целиком |

## 7. Что не реализовано (осознанно)

- **Автоотключение по истечении.** Срок проверяется на чтении, но Marzban-пользователь
  не выключается планировщиком. Для боевого режима нужен cron-джоб (в Marzban или в
  боте), который раз в сутки ставит `disabled` истёкшим.
- **Офлайн-ключи** (получатель без Telegram). Сейчас ключ всегда привязан к
  Telegram-пользователю; выдать ссылку «на руки» без получателя нельзя.
- **HTTP-API для ключей.** Намеренно нет: у API бота нет аутентификации, а ключи —
  это доступ.
- **Пакетная выдача по списку.** `createKeys` умеет пачку, но UI создаёт по одному.

## 10. Как проверить

Автотесты (mock-режим, сеть не нужна):

```bash
cd bot
npm run typecheck
npm test          # 41 тест, из них 17 — ключи
```

Ручной сценарий в Telegram (mock):

1. `/key new vpn_1m тест` → в ответ придёт код.
2. `/key issue <код> <ваш Telegram ID>` → придёт ссылка-подписка.
3. `/key info <код>` → статус `active`, получатель, срок.
4. «💎 Тарифы» → купить → «💳 Оплатить (демо)» → в `/key list` у пользователя
   тот же ключ с обновлённым сроком и `order_id`.
5. `/key revoke <код>` → статус `revoked`, «📦 Моя подписка» показывает «Истекла».

## 11. Миграция и откат

Таблица создаётся автоматически при старте (`CREATE TABLE IF NOT EXISTS`),
миграции не нужны. Существующие пользователи продолжают работать: подписка
хранится в `users`, ключ — дополнительная запись.

Откат подсистемы: удалить вызовы `recordSubscriptionKey` из
`src/services/subscriptions.ts` и вернуть `provision.ts` к `telegramId`. Данные в
таблице `keys` можно оставить — они ни на что не влияют.
